# Go Email Deliverability for Edtech Password Resets: Provider Evidence, SPF, DKIM

Short answer: for an education product, choose the mail transport that lets your team prove what happened to a password-reset message. Custom-domain authentication, a durable suppression decision, and bounce evidence should be separate controls. The provider is secondary. At 3am, the useful question is not which dashboard is green; it is which page fired, for which learner, and on which delivery signal.

A reset message is operationally different from a newsletter. It is a short-lived security instrument, usually valid for 10 minutes in the application, and a learner who cannot receive it is blocked from class. I would therefore test the full path with a seeded mailbox and a deliberately invalid address before signing off a transport: authenticated submission, accepted response, delivery event, bounce classification, suppression behavior, and a page only when the failure affects real reset traffic.

The page must be actionable.

Green is not proof.

## Which provider evidence proves password reset email deliverability?

The page should fire on a meaningful loss of reset delivery, not on every rejected recipient. A single hard bounce is a data point. A rising rate of permanent failures for one sending domain, a sudden absence of delivery events after successful submission, or a queue that cannot hand work to the transport is an incident signal. Those are different failures and should not share one counter.

Start with the message identifier generated by the application. Carry it through the submission response and event consumer, while storing recipient hash, tenant or school identifier, authentication result, event type, and provider response category. Do not log the reset token or put it in a URL-bearing log line. OWASP recommends that reset tokens be generated with a secure method, expire, be single-use, and produce a consistent user-facing response so the address cannot be enumerated. Deliverability instrumentation must preserve those properties rather than turning debugging into a secret-leak path.

The page should answer three questions quickly: did the application enqueue the message, did the transport accept it, and did the receiving system report delivery or rejection? A dashboard that only shows accepted submissions answers none of them.

For a school district, I would keep the trace narrow enough to inspect during an incident but rich enough to separate a bad address from a broken sender identity. One event should show the application message ID, tenant, hashed recipient, template revision, authentication result, submission time, transport response, and the eventual event timestamp. The next event should preserve the normalized category and the original response text. That gives the responder a path from a learner’s failed recovery attempt to a specific boundary without exposing the reset token, and it makes a replay safe to reason about because the suppression decision can be keyed by message ID and event type rather than by the order in which duplicate callbacks arrived.

## Is custom-domain authentication an ownership test or a transport feature?

It is both, and confusing the two causes avoidable incidents. SPF authorizes hosts for a domain; DKIM signs selected headers and the message body; DMARC evaluates alignment between the visible From domain and an authenticated identity. RFC 7208, RFC 6376, and RFC 7489 describe those mechanisms and their boundaries. A transport can submit mail successfully while the recipient later rejects it because the visible identity does not align with the organization’s policy.

Treat DNS records as owned production configuration. Record which team approves changes, which domain is used for the reset From address, which DKIM selector is active, and how key rotation is tested. Keep the reset stream distinct from bulk mail where the organization can reasonably do so; reputation and suppression decisions are easier to reason about when unrelated traffic does not share the same operational signal.

The test is not “the provider gave us a green check.” Send a reset to a controlled mailbox, inspect the received headers, confirm the DKIM result and aligned domain, then remove or rotate the test selector according to the change plan. Capture the evidence with a timestamp and message identifier. A screenshot is not an audit trail.

## Where do bounce handling and suppression belong?

Bounce handling belongs at the boundary between transport events and application policy. SMTP status codes provide useful categories, but the receiving system’s text is not a stable business rule. A permanent address failure should normally suppress future reset attempts until an explicit correction occurs. A temporary deferral should be retried under a bounded policy. A complaint or abuse signal should be treated as a safety event, even if the address has not technically bounced.

The suppression record needs a reason, first-seen time, last-seen time, source event, and a controlled release path. Keep the raw event for investigation, but make the application decision explicit. This prevents a provider-specific status string from silently deciding whether a learner can recover an account. It also makes ownership testable: the transport reports facts; the account or communications service owns the decision to send again.

The trade-off is real: a transport-managed suppression list can simplify event handling, but it can hide policy ownership; an application-owned list gives auditability, but demands idempotent event processing and a release workflow. Neither choice fixes a misaligned domain or a bad threshold.

Here is the narrow interface I would put behind the reset workflow. It leaves event interpretation outside the token-generating code and makes the failure policy visible in review.

```go
type MailEvent struct {
    MessageID string
    Kind      string
    SMTPCode  int
    Address   string
    Reason    string
}

func SuppressionAction(e MailEvent) string {
    switch {
    case e.Kind == "complaint":
        return "suppress"
    case e.Kind == "bounce" && e.SMTPCode >= 500:
        return "suppress"
    case e.Kind == "bounce" && e.SMTPCode >= 400:
        return "retry_with_backoff"
    default:
        return "record_only"
    }
}
```

This is policy, not a claim that every recipient maps perfectly to a three-digit code. Preserve the original event and review ambiguous cases. SMTP’s enhanced status codes, described in RFC 3463 and its updates, help classification; they do not remove the need for an operational decision.

## What does the 3am test actually measure?

Run a small, repeatable matrix during deployment and after DNS or template changes: a valid mailbox, an unknown mailbox in a controlled domain, a temporary rejection if the test environment supports one, and a mailbox that reports the received headers. Check that the reset link expires at the intended interval, that a second use fails, that the visible response does not reveal account existence, and that the message remains readable without relying on a remote image.

Then trace one message end to end. The first useful alert is a missing transition, not an attractive chart: a submitted reset with no transport outcome after a bounded window. The next alert is a domain-level change in permanent failures compared with a recent baseline. Thresholds must be chosen against reset volume; a fixed count will page a small school and miss a large one. Rate, minimum sample size, and persistence belong in the rule.

False positives have a security cost as well as an on-call cost. If every transient deferral pages, responders learn to dismiss the alarm. If the threshold waits for thousands of failures, a district may spend an hour unable to recover accounts. The right threshold is the one the team can explain in terms of affected reset attempts, elapsed time, and the next safe action.
